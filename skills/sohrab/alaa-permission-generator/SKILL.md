# Alaa Permission Generator

Use `alaa-permission-catalog` as the only allocator of coarse permission names and global bitmap IDs. Keep auth as the
runtime issuer of `prm`, `prv`, and `av`; keep the gateway as the trusted-header boundary; keep object-level OpenFGA
relations outside this workflow.

## Start here

1. Read the target repository's `AGENTS.md` and current permission enforcement code.
2. Read `references/catalog-workflow.md` completely.
3. Read `references/laravel-consumer.md` for `config/permissions.php` consumers.
4. Read `references/go-consumer.md` for generated Go maps and bitmap decoders.
5. Read `references/typescript-consumer.md` for TypeScript aggregate consumers, all-active generation, and frontend
   UI-hint decoding.
6. Load `$alaa-services-contract` and `$alaa-trust-gateway-auth` for every implementation; load `$alaa-golang` for Go,
   `$alaa-laravel-architecture` and `$alaa-php-clean-code` for Laravel, or `$alaa-vue-typescript-clean-code` and
   `$alaa-mono-package` for TypeScript. Add `$alaa-security-review` whenever a consumer reads token claims.
7. Treat catalog editing, generated source application, auth seed application, and user/role assignment as separately
   reviewable operations. Perform only the operations authorized by the request.

## Non-negotiable contract

- Never allocate an ID outside `catalog/permissions.json`.
- Never reuse, renumber, or delete a published `bitmap_id`; deprecate or reserve it.
- Always set `bit_index = bitmap_id - 1`.
- Decode raw unpadded base64url, with bits packed least-significant-bit first within each byte.
- Ignore unknown bits in a downstream service, but reject a protected request that resolves to zero known permissions.
- Generate an auth seed target plus the owning service target for each active downstream permission. Aggregate
  consumers are the exception: they are scoped `all_active` and must not appear in any permission's `generated_targets`.
- Register a permission owner in the `services` array and an aggregate consumer in the `aggregate_consumers` array of
  `catalog/services.json`. An aggregate consumer never owns a `service_key`.
- Commit the generated consumer artifact; do not fetch the catalog at runtime.
- Do not let environment variables, JSON files, database rows, or hand-written maps override the generated consumer map.
- Treat a frontend decode of `prm`, `prv`, or `av` as an unverified UI hint, never as authorization, and never let an
  empty frontend permission set invalidate a session.
- Do not hand-edit files carrying `Code generated by alaa-permission-catalog. DO NOT EDIT.`
- Do not equate coarse catalog permissions with entitlement-platform OpenFGA `can_*` relations.
- Do not modify JWT claim semantics, gateway sanitization, or user/role assignments unless explicitly requested.

## When NOT to use

- Do not use for object-level OpenFGA model relations, tuples, or `can_*` endpoint mappings; use `$openfga`.
- Do not use for gateway route ACLs or JWT verification without a catalog change; use `$alaa-trust-gateway-auth`.
- Do not use for assigning an already-defined permission to a user or role unless the task also changes catalog artifacts.
- Do not use for purely local feature authorization that does not consume the shared coarse permission bitmap.

## Standard execution sequence

1. Inspect current service routes, middleware, permission names, and existing catalog entries.
2. Add or correct the descriptor in `catalog/services.json`: a permission owner under `services`, an aggregate consumer
   under `aggregate_consumers`.
3. Allocate new IDs after the highest allocated ID and add full entries to `catalog/permissions.json`.
4. Run import, strict validation, generation, strict drift checking, summary, and tests.
5. Review the generated auth seed, consumer artifacts, and drift report.
6. Apply only the approved generated artifact to its exact source path in the owning repository.
7. Make the consumer use generated names and IDs directly; remove alternate runtime mapping sources.
8. Run the target repository's focused and full validation.
9. Re-run the catalog loop so the importer observes the applied consumer artifact and aggregate drift verifies it.
10. Report auth seed application and user/role assignment as explicit remaining work when they were not in scope.

Canonical catalog loop from the `alaa-permission-catalog` root:

```bash
php scripts/permission_catalog.php import
php scripts/permission_catalog.php validate --strict
php scripts/permission_catalog.php generate
php scripts/permission_catalog.php check-drift --strict
php scripts/permission_catalog.php summary
php tests/run.php
```

## Stop conditions

Stop and report instead of guessing when:

- a requested name or ID conflicts with an active, deprecated, reserved, or legacy entry;
- source code and catalog ownership disagree;
- drift contains a fatal or error finding, including any `AGGREGATE_CONSUMER_*` code above warning severity;
- the generated target escapes its declared repository/path boundary;
- applying the artifact would overwrite unrelated user changes;
- the service's trusted-header or bitmap semantics differ from the shared contract;
- the request implicitly requires auth seed application or external user/role mutation without authorization.

## Completion evidence

Provide the allocated names and IDs, generated and applied paths, drift counts, target tests, and remaining auth-owned
operations. Keep catalog truth, source-repository truth, and unapplied generated proposals distinct.
