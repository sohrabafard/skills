# Aggregate Collections And Consumer Repositories

Read this file when one Postman collection is built by merging the collections of several services, or when a repository holds its own copy of a script this skill owns.

## What an aggregate collection is

An aggregate collection is a single Postman artifact generated by merging the service-local collections of several services, rewritten so every request targets one shared front door instead of each service's own host. A gateway, an edge proxy, or a BFF repository owns that artifact; the services own their own collections.

Two artifacts therefore exist for the same operation, and they are not copies of each other:

| Artifact | Owner | Auth model | Host |
|---|---|---|---|
| Service-local collection | the service repository | whatever the service accepts directly, including trusted internal headers | that service's own base URL |
| Aggregate collection | the fronting repository | the auth the external client actually presents at the front door | one shared base URL plus a per-service route prefix |

An aggregate whose requests still carry the service-local auth model teaches callers to send headers the front door strips, so every request in it fails. Keep the two auth models distinct on purpose.

## Ownership split

Set the boundary by asking which repository the fact belongs to, not which repository is convenient.

**This skill owns** the Postman format rules, the variable and script rules, the validation scripts, and the doctrine on this page. Every rule here applies to any service.

**The fronting repository owns** its own merge program and the data that program reads:

- the source registry: which service contributes which collection and environment file, and where those files live
- the route prefix per service, and the variable that carries it
- the public-versus-protected route allowlist
- the set of trusted internal headers to strip
- service display names and per-service import rules
- any per-service transformation that exists only because one service's collection is shaped unusually

None of that data may move into this skill. A shared skill that carried one platform's service list would load that list into every other service that triggers this skill, and the first agent to read it would treat another platform's routes as its own.

## The rule for a consumer repository holding a copy of a skill script

A repository whose CI runs a skill script cannot depend on the skill being installed on the CI runner, so it keeps its own copy. That is allowed on all four terms below. Forking the script is not allowed on any terms.

- Change the script in this skill first. This skill is the source of truth for every script under `scripts/`.
- Then make the consumer repository's copy byte-identical to the skill's copy, in the same task.
- Never add a repository-specific check, flag, or constant to the consumer copy. Pass repository-specific data in as command-line arguments instead, which is why every script here takes its inputs as arguments.
- Prove the copies match before closing. Below, `$SKILL_DIR` is the directory holding this skill's `SKILL.md`, and the example consumer copy sits at `<repo>/scripts/postman/audit_collection_contract.py`:

```shell
diff -u "$SKILL_DIR/scripts/audit_collection_contract.py" scripts/postman/audit_collection_contract.py
```

Empty output means the copies are in sync. Any output means the consumer repository is running different logic from the skill, which makes its CI result unreproducible from the skill; re-sync it from the skill and rerun the repository's own gate before closing.

## Invariants a merge program must hold

Verify each of these against the merge program before trusting its output. Each one has a failure that is silent without the check.

1. **Namespaced variables.** A source variable becomes a per-service name in the aggregate, except for the few genuinely shared names the aggregate defines once. Without this, two services that both use `baseUrl` or `token` overwrite each other at runtime.
2. **Host and prefix rewriting.** Every request URL, and every saved response `originalRequest` URL, resolves to the shared base URL plus the service's prefix variable. A saved response left on the service-local host documents a request the aggregate cannot send.
3. **Trusted-header stripping.** Headers the front door injects or removes are deleted from both requests and saved examples. Leaving one in teaches a caller to spoof it.
4. **Script promotion.** The merge program promotes any source script found under `request.event`, as `42-scripts-and-state-capture.md` requires, instead of copying it through. A merge that copies it through produces a collection whose captures never run.
5. **Saved-response conservation.** The number of saved responses admitted by the import filter equals the number written out. A merge that drops examples degrades the contract without failing.
6. **No unnamespaced script writes.** After merging, every variable a script writes is either a declared shared name or carries its service's namespace, and every one of them exists in the generated environment. Otherwise a capture writes to a variable no request reads.
7. **Exclusion filters hold.** Service-only routes — internal service-to-service paths, metrics endpoints, and anything the front door does not route — are absent from the aggregate, and each exclusion is logged. An internal route published as a client request is a security defect, not a documentation defect.
8. **Deterministic output.** Regenerating from unchanged sources produces byte-identical files, which requires stable collection and environment IDs rather than fresh random ones. Without this, every regeneration produces an unreviewable diff.

Invariants 4, 5, and 6 each produce an artifact that looks correct and does not work, so a merge program raises an error on them and never a warning. A warning on these three is a defect in the merge program.

## Which repository to fix

`10-scope-and-trigger-rules.md` already forbids hand-editing a generator-owned artifact. An aggregate adds the question that rule does not answer: which of the two repositories to change. Work down this list and stop at the first match.

1. The request content is wrong — the path, body, parameters, examples, or prose describe the service incorrectly. Fix the service-local collection in the service repository. Nothing in the fronting repository changes.
2. The prefix, auth boundary, public-route allowlist, header stripping, or import filter is wrong. Fix the merge program's data or rules in the fronting repository.
3. Then regenerate with the fronting repository's own command, review the generated diff, and run that repository's Postman and drift gates.

Editing the generated file instead is worth naming precisely, because the edit appears to work: the next regeneration overwrites it, the drift gate then compares the artifact against its real sources and fails, and until someone regenerates, the artifact describes behavior no source declares.

## Worked example

The `gateway` repository is the reference implementation. `scripts/postman/generate_gateway_collection.sh` merges eight service-local collections into one gateway-facing aggregate under `docs/postman/`, and `docs/postman/gateway-postman-maintenance.md` documents its registry, its per-constant change procedure, and its change matrix. Read those two files before changing an aggregate in any repository; they hold the operational detail this page deliberately does not restate.

That generator stays in `gateway` and is not moved into this skill: its transformations are defined by gateway's route prefixes, public-route allowlist, trusted-header set, and per-service exceptions, so the logic and the data are not separable without inventing a configuration format richer than the one platform that would use it.
