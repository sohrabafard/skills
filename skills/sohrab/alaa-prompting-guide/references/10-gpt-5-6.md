# GPT-5.6

OpenAI's current frontier generation, released 9 July 2026. All three variants share a 1,050,000-token context window, 128,000 max output tokens, and a 16 February 2026 knowledge cutoff. Treat every limit, price, and beta status below as volatile.

## Model selection

Three variants, one alias:

| Model ID | Position | Price (input / output per MTok) |
|---|---|---|
| `gpt-5.6-sol` | Flagship. Complex professional work: coding, knowledge work, cybersecurity, science. `gpt-5.6` aliases this. | $5 / $30 |
| `gpt-5.6-terra` | Intelligence/cost balance for everyday work. | $2.50 / $15 |
| `gpt-5.6-luna` | Efficient, high-volume and cost-sensitive workloads. | $1 / $6 |

The bare `gpt-5.6` alias routes to the flagship, so an unqualified model string silently buys Sol pricing. Name the variant explicitly in any generated configuration. All three support reasoning, functions, web search, file search, and computer use.

Prefer the Responses API for reasoning, tools, and multi-turn workflows. Selection heuristic: start on Terra for routine agentic and coding work, promote to Sol where a measured quality gap justifies the price step, and drop to Luna for bulk classification, extraction, and fan-out subagent lanes where the lane's output is checked downstream. Sweep the pair (variant × effort) rather than either axis alone — a lower variant at higher effort frequently beats a higher variant at lower effort on cost per accepted result.

## Reasoning effort

`reasoning.effort` supports `none`, `low`, `medium`, `high`, `xhigh`, and `max`. When omitted it defaults to `medium`, in both standard and Pro mode.

Sizing effort is not "pick a level" — it is a two-point comparison:

1. **Start from your current baseline level**, whatever workload it was tuned on.
2. **Then test one level lower.** This generation frequently holds output quality at a lower effort setting for materially fewer reasoning tokens, so a level that was necessary before is often one step above what's needed now. Ship the lower level only when your own evals show quality holds.
3. **If you were running `none`, test `low`** where the workflow benefits from any reasoning or tool use.

Reserve `max` for measured quality-first gains, not as a default posture. Effort and Pro mode are independent controls; setting one does not imply the other. For the cross-model decision procedure, read `references/50-effort-and-thinking.md`.

## Lean prompts

OpenAI's internal testing on this generation found that trimming prompts improved evaluation scores by roughly **10–15%** while cutting total tokens by **41–66%** and cost by **33–67%**. Both directions moved at once: leanness here is a quality lever, not only a cost lever. That result is what makes prompt trimming a required step for any prompt on this generation, not an optional cleanup.

Three concrete rules follow, and they are the operative content of the finding:

- **State each instruction once.** Repeating a rule in the system prompt, the developer message, and a tool description does not reinforce it; it competes with itself and burns context. Give every rule exactly one owning location.
- **Expose only task-relevant tools, with concise descriptions.** A tool the task cannot use is a distractor with a token price. Trim the roster to what this task needs, and keep each description to its contract — inputs, outputs, errors, routing constraints — not prose about when a human might find it handy.
- **Keep only examples that encode a requirement or close a measured gap.** An example that demonstrates a format the schema already enforces is dead weight. An example that pins down an ambiguous requirement, or that was added because an eval failed without it, earns its tokens. Delete the rest.

Applied order for an existing prompt: cut duplicated instructions first, then optional background and generic reassurance, then examples that fail the requirement/gap test, then re-measure. Do not trim required facts, decisions, caveats, or next steps. Re-baseline task success, answer completeness, evidence quality, tokens, latency, and cost together after every trim — fewer tokens and fewer calls are improvements only when the final answer still meets the quality bar.

## Prompt contract

- Start with the smallest prompt and task-relevant tool set that passes representative evals; add instructions or examples only for observed gaps.
- State the outcome, relevant context, constraints, required evidence, success criteria, output shape, and stopping condition. Avoid process scripts unless order is part of correctness.
- Define authority once: inspection/reporting requests do not authorize implementation; change requests authorize scoped local edits and non-destructive validation; external writes, destructive actions, purchases, and material scope expansion require confirmation.
- Use lightweight, task-specific structure. Replace generic warmth with concrete tone such as direct, tactful, and free of canned reassurance.
- For agentic work, require persistence until verified completion or a genuine blocker; allow reasonable assumptions within scope and require disclosure afterward.
- State reuse, delegation, tests, escalation, and parent-agent reconciliation explicitly. Replace legacy ALWAYS/NEVER wording with decision rules where judgment is required.
- Put tool inputs, outputs, errors, and routing constraints in tool descriptions and schemas. Prefer structured outputs over prose-described JSON.
- For long tool runs, require one short preamble before the first call.

## Programmatic Tool Calling

The model writes JavaScript that calls eligible tools, passes results between calls, and processes intermediate outputs inside a hosted, isolated V8 runtime with top-level `await`. The runtime has no Node.js, no package installation, no direct network or filesystem access, no subprocesses, and no state persisted between executions; programs reach the outside world only through enabled tools and emit results via `text(...)` or `image(...)`.

Enable it by adding a hosted tool of `"type": "programmatic_tool_calling"`, then set `allowed_callers` per tool: omitted or `["direct"]` for model-only calls, `["programmatic"]` for code-only, `["direct", "programmatic"]` for both. Eligible tool types include `function` and `custom`, `mcp`, `apply_patch`, local and hosted `shell`, and `code_interpreter`. Define `output_schema` on functions so the generated program can address returned fields reliably rather than parsing prose.

**When it pays:** bounded, tool-heavy stages where several results need filtering, joining, ranking, deduplication, aggregation, or validation, and where dependent calls have predictable data flow. The win is that intermediate volume never enters the model's context.

**When to use direct calls instead:** one call suffices; intermediate outputs are already small; each result could change the model's next decision; the action requires approval; or native citations and artifacts must survive to the final answer.

When specifying a PTC stage in a prompt, define the stage boundary, the eligible tools, the output schema and required evidence, concurrency/retry/stop limits, and the handoff back to direct calls. Keep operations idempotent, validate arguments and permissions server-side regardless of caller, and require application-level approval for high-impact actions no matter which caller initiates them. Benchmark a PTC stage against direct calls on representative tasks before adopting it — the win depends on the shape of the specific pipeline, not a blanket rule.

## Multi-agent coordination and parallel subagents

A beta feature of the Responses API, available with all GPT-5.6 models behind the `responses_multi_agent=v1` beta header and enabled with `multi_agent.enabled`. One instance coordinates subagents in parallel and synthesizes their results, which reduces wall-clock time on tasks that divide cleanly into independent workstreams.

Agents occupy a tree addressed by path (`/root`, `/root/researcher`, `/root/reviewer/tester`). `max_concurrent_subagents` bounds how many are simultaneously active across the whole tree, excluding the root and including all descendants; the documented default is `3` and OpenAI recommends it for most workloads. Coordination happens through hosted actions surfaced as `multi_agent_call` items — `spawn_agent`, `send_message`, `followup_task`, `wait_agent`, `interrupt_agent`, `list_agents` — which the platform executes, not your application. WebSocket transport is recommended over HTTP: function outputs inject immediately via `response.inject` events instead of requiring a round trip per resumption.

Documented limitations: no `/responses/compact` endpoint, no `reasoning.summary`, no `max_tool_calls`, and server-side compaction applies independently to the root and to each subagent.

Prompt-side, this is where the family's reticence matters. Codex and GPT-5.6 do not fan out unprompted, so a multi-agent prompt must **authorize** delegation positively, name lane ownership and disjoint scopes, state the concurrency and stop limits, and assign synthesis responsibility to exactly one agent. See `references/06-invocation-and-composition.md` for the polarity rule and `references/80-subagent-authoring.md` for lane definitions. For the Codex app/CLI subagent mechanism, which is separate from this API feature, read `references/11-codex-runtime-features.md`.

## Prompt caching

Implicit caching still works. Explicit caching lets you mark reusable prefixes, and it carries a cost asymmetry that decides when it is worth using: **cache writes bill at 1.25× the uncached input rate, while cache reads are discounted.** A prefix that is written once and read many times pays for itself; a prefix that is written and rarely read costs more than not caching at all.

The operative rules: mark only prefixes with a genuinely high read-to-write ratio, avoid volatile content inside the marked region, order the prompt so stable system and tool content precedes volatile user and retrieved content, and monitor cache reads versus writes rather than assuming the win. `prompt_cache_options.ttl` replaces the deprecated `prompt_cache_retention`. Note also that changing reasoning effort between requests invalidates cached prefixes — hold effort constant within a cached conversation and vary it across workloads.

## Persisted reasoning across turns

`reasoning.context` controls whether reasoning carries across turns, with `auto` as the default. Set `all_turns` with `previous_response_id` when the task's goals, assumptions, and priorities stay stable across turns — long agentic runs against one objective are the clear case. Set `current_turn` when earlier reasoning is stale or the turn changes direction, since carrying stale reasoning forward anchors the model to a superseded plan. When managing history manually, preserve returned reasoning items rather than dropping them.

## Pro mode

Enable with `reasoning.mode: "pro"`. Do not invent a Pro model slug, and do not attempt to reach it by prompting the model to "think harder" — mode and effort are independent parameters. Tokens bill at the selected model's standard rates.

It is worth using when a marginal quality improvement materially changes the outcome *and* the task is hard enough to benefit: complex optimization, high-value coding, high-stakes review. It is not worth using on routine work, on tasks that are bounded by retrieval or tool quality rather than reasoning depth, or as a blanket default — the extra work is spent whether or not the task needed it.

## Output length control

Use `text.verbosity` (`low`, `medium`, `high`) to set a task default, and specify concrete content requirements in the prompt on top of it. Prioritize required content over generic "be concise" instructions: naming what must appear is a more reliable length control than asking for brevity, which trims the wrong things. Treat verbosity as independent of reasoning effort — lowering effort reduces thinking volume, not answer length.

## Minimal reusable fragment

```text
Deliver <outcome> using <context/tools> within <scope>.
Preserve <invariants>. Done means <checkable criteria> verified by <evidence>.
For analysis/review, inspect and report only. For requested changes, edit in scope and run non-destructive checks.
Confirm before external writes, destructive actions, purchases, or material scope expansion.
Continue until done or genuinely blocked; then report the blocker and what would unblock it.
Keep required facts, caveats, decisions, and next actions; trim repetition and optional background first.
```

## Caveats

Verified against live documentation on 24 July 2026. Time-sensitive: prices, the 1,050,000-token context window, 128,000 max output tokens, the February 2026 cutoff, the `max_concurrent_subagents` default of 3, the 1.25× cache-write rate, and the beta status of multi-agent are current published values and should be re-fetched before being quoted elsewhere. The 10–15% / 41–66% / 33–67% figures are OpenAI's measurement for this generation on their own evaluation set, not a general law — re-verify on the next generation and on your own workloads.

Separately, OpenAI's launch announcement describes an `ultra` tier that coordinates four agents in parallel by default, gated to specific ChatGPT and Codex plan tiers. That is a product-surface setting on those apps, not a documented value of the API's `reasoning.effort` parameter, which the API reference lists as `none` through `max`. Do not write `ultra` into an API configuration on the strength of the announcement alone.
