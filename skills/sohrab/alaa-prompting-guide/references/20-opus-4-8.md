# Claude Opus 4.8

API model id `claude-opus-4-8`. Anthropic's most capable Opus-tier model for complex reasoning, long-horizon agentic coding, knowledge work, vision-heavy analysis, memory-heavy work, and code review. It is a good default for architecture-sensitive review, subtle bug finding, and multi-step production-readiness analysis. Existing Opus 4.7 prompts usually transfer, but re-check effort, verbosity, tool-use, subagent, and frontend/design scaffolding before treating an old prompt as tuned.

Pick Opus 4.8 over Sonnet 5 when the task is genuinely reasoning-heavy, architecture-sensitive, or review-oriented; pick it over Fable 5 when the task does not need Fable's higher capability ceiling, longer-run autonomy, or steeper cost (see `references/90-model-selection.md`).

## Migration and API notes

When migrating from Opus 4.7, verify the live Anthropic docs before copying exact API details. The sensitive surfaces are sampling-parameter behavior, the default effort level, 1M context-window defaults, mid-conversation system-message support, refusal stop details, and any exact output/context limits. Keep these as freshness-sensitive claims, not permanent constants.

## Effort and thinking

`effort` (low / medium / high / xhigh / max) is the main intelligence-vs-cost lever. Start at `xhigh` for coding and agentic use cases, use `high` as the floor for most intelligence-sensitive work, step down to `medium` or `low` only after evals show quality holds, and reserve `max` for genuinely frontier problems. Opus 4.8 follows low and medium effort levels literally: it scopes tightly to the request and is less likely to go beyond what was asked, so raise effort before trying to prompt around shallow reasoning.

Thinking is off unless `thinking: {type: "adaptive"}` is set. If adaptive thinking triggers too often, steer it directly:

```text
Thinking adds latency; use it only when it will meaningfully improve answer quality, usually for multi-step reasoning. When in doubt, respond directly.
```

At `xhigh` or `max`, set a generous `max_tokens` budget, starting around 64k, so the model has room for thinking, tool calls, and subagents.

## Response length, tone, and progress updates

Opus 4.8 calibrates response length to task complexity. Simple lookup prompts tend to produce shorter answers; open-ended analysis can produce much longer ones. If a product needs a fixed voice, concision level, or output length, state it directly and provide positive examples. For concise output, use a short instruction like:

```text
Provide concise, focused responses. Skip non-essential context, and keep examples minimal.
```

Opus 4.8 tends toward a direct, opinionated style with less validation-forward phrasing and sparse emoji use. Add warmth explicitly when the product voice needs it. During long agentic traces, it usually gives better progress updates than older prompts forced through rigid counters. Remove scaffolding such as "after every 3 tool calls, summarize progress" unless the product UX needs it; instead describe what a useful progress update should include.

## Prompting techniques that matter most

- Be explicit about desired output, format, scope, and constraints; state when an instruction applies to every section, file, or item.
- Use XML tags for complex prompts that contain role, instructions, context, examples, and input documents.
- For long-context work, put long documents near the top of the prompt and the final task/query near the end; ask Claude to cite or quote the relevant passages before answering when evidence traceability matters.
- Opus 4.8 favors reasoning over reflexive tool calls. Raise effort and give explicit tool-triggering rules when search, code inspection, or browser/computer use is expected.
- It under-spawns subagents by default. Give explicit delegation guidance when a task decomposes into independent lanes.
- Use direct action verbs such as `change`, `implement`, `verify`, or `report only`; Opus 4.8 does not silently generalize an implied action.
- Dial back heavy imperative tool language such as "CRITICAL: MUST" unless the requirement is truly non-negotiable; plain trigger rules are usually enough.
- For long-horizon work, use structured state files, progress notes, and commits/checkpoints; tell the model that context may auto-compact so it should not stop early.
- Add confirm-before-destructive-action guidance for shared systems or irreversible actions.
- Add an explicit anti-overengineering instruction when the task is narrow.

## Subagents

Opus 4.8 tends to spawn fewer subagents than prior Opus prompts may expect. Use concise guidance such as:

```text
Do not spawn a subagent for work you can complete directly from the visible context.
Spawn multiple subagents in the same turn when the task fans out across independent files, modules, or hypotheses.
```

For Claude Code's actual Agent tool, `/loop`, Workflow tool, plan mode / Ultraplan, and `/goal`, read `references/41-claude-code-runtime-features.md`.

## Frontend and design defaults

Opus 4.8 has a strong default visual style: warm cream/off-white surfaces, serif display type, italic accents, and terracotta/amber accents. That can be good for editorial, hospitality, portfolio, or boutique product briefs, but it is usually wrong for dashboards, dev tools, fintech, healthcare, admin panels, and enterprise apps.

Generic negative instructions such as "do not use cream" often shift the model to another fixed look. Use one of these patterns instead:

- Specify a concrete visual system: palette, typography direction, layout rhythm, radius, density, imagery rules, and motion restraint.
- Ask for 3-4 distinct visual directions first, then have the user choose one before implementation.

For frontend work where generic AI aesthetics are a risk, add a short aesthetics block that requires context-specific typography, color, layout, motion, and interaction choices, and explicitly rejects generic purple gradients, overused default fonts, and cookie-cutter card layouts.

## Interactive coding products

Opus 4.8 can spend more tokens in synchronous, multi-turn coding sessions because it reasons again after each user turn. For coding products, prefer `xhigh` or `high` effort, front-load intent and constraints in the first human turn, reduce unnecessary clarification loops, and support an autonomous or auto-mode flow where the model can proceed until it is done or genuinely blocked.

## Code review harnesses

Opus 4.8 is strong at finding bugs, but it follows conservative review prompts literally. A harness tuned with phrases like "only report high-severity issues" may lower reported recall even when investigation depth is good. For coverage-first finding stages, use:

```text
Report every issue you find, including uncertain or low-severity ones. Do not filter for importance or confidence in this stage. Include confidence and estimated severity so a later verification or ranking step can filter them.
```

If a single pass must self-filter, define the bar concretely, for example: report any bug that could cause incorrect behavior, a test failure, data loss, security exposure, or a misleading result; omit only pure style or naming preferences.

## Computer use

For computer-use workflows, keep resolution practical. Treat 2576px / 3.75MP as the maximum envelope, prefer 1080p as the default balance of accuracy and cost, and use 720p or 1366x768 for cost-sensitive workloads after testing.

## Ready-to-use review-prompt skeleton

This is the shape `$alaa-workflow`'s own phase-prompt-pack template already uses for Opus review:

```text
<role>Staff-level reviewer. Be skeptical, concrete, and evidence-based.</role>
<context>Read first: <files/plan/diff>.</context>
<must_check>Correctness, production readiness, security, observability, performance, clean code, architecture,
tests that would fail against plausible broken implementations, and validation evidence.</must_check>
<output_format>1. VERDICT (APPROVED | APPROVED-WITH-NITS | CHANGES-REQUESTED) 2. FINDINGS (file:line, severity, confidence, why, fix)
3. RISKS/NITS 4. OUT-OF-SCOPE RECOMMENDATIONS 5. GATE EVIDENCE</output_format>
```
