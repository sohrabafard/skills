# Claude Opus 4.8

API model id `claude-opus-4-8`. Anthropic's most capable Opus-tier model for complex reasoning, long-horizon agentic coding, and high-autonomy work, built on Opus 4.7 with better long-horizon agentic coding, more reliable effort calibration, and better tool triggering. 1M-token context by default, 128k max output, adaptive thinking. Notably strong at finding bugs — a good default for code-review harnesses and complex multi-step review.

Pick Opus 4.8 over Sonnet 5 when the task is genuinely reasoning-heavy, architecture-sensitive, or review-oriented; pick it over Fable 5 when the task does not need Fable's higher capability ceiling and steeper cost (see `references/90-model-selection.md`).

## Effort and thinking

`effort` (an `output_config.effort` field: low / medium / high / xhigh / max) is the primary lever — a behavioral signal affecting all response tokens (text, tool calls, thinking), not a hard token budget. **Opus 4.8 defaults to `high`.** Official guidance: start at `xhigh` for coding/agentic work, use `high` as the floor for other intelligence-sensitive work, step down to `medium`/`low` only once evals confirm quality holds, and reserve `max` for genuinely frontier problems. Opus 4.8 respects effort levels strictly, especially at low/medium — it scopes work tightly to what was asked rather than going above and beyond on its own, so if reasoning looks shallow, raise effort rather than prompting around it.

Thinking is **off by default**; set `thinking: {type: "adaptive"}` explicitly to enable it. Manual `budget_tokens` thinking is unsupported and errors — effort is the only depth lever now. If adaptive thinking triggers more than wanted, add explicit throttling language ("think only when it will meaningfully improve answer quality"). At `xhigh`/`max`, set a generous `max_tokens` (start around 64k) so there's room to think and act across tool calls and subagents.

## Tone

Concise, natural, grounded by default: fact-based progress reports rather than self-celebratory updates, conversational rather than machine-like, sometimes skipping a summary after tool calls to move straight to the next action. Response length is not a fixed verbosity setting — it scales to perceived task complexity. Steer tone/length with explicit style instructions and *positive* worked examples rather than negative "don't do X" instructions, since Opus 4.8 follows literal instructions closely and negative framing tends to just shift its default rather than diversify it.

## Prompting techniques that matter most

- Be clear and direct about desired output, format, and constraints; use numbered/bulleted steps when order matters; explicitly ask for above-and-beyond effort rather than relying on inference.
- Use XML tags to structure complex prompts — wrap instructions, context, examples, and input documents in distinct consistent tags.
- For long-context work, put long documents near the top of the prompt, above the query, and ask Claude to quote relevant passages before answering.
- Opus 4.8 favors reasoning over reflexive tool calls — raise effort and give explicit tool-triggering instructions if you need more aggressive tool use; it already parallelizes independent tool calls well by default.
- **It under-spawns subagents by default** (the opposite failure mode from Opus 4.6, which over-spawned) — give explicit delegation guidance when you want proactive fan-out.
- Follows instructions literally and does not silently generalize scope — state scope explicitly, use direct action verbs (change, implement) when you want edits rather than suggestions.
- Dial back aggressive imperative tool-triggering language ("CRITICAL: you MUST") — Opus 4.8 is responsive enough to plain "use this tool when..." phrasing and may overtrigger on heavy-handed imperatives.
- For long-horizon/multi-context-window work: use structured state files, freeform progress notes, and commits as checkpoints, and tell it explicitly that context will be auto-compacted so it should not stop early.
- Add explicit confirm-before-destructive-action guidance for autonomous loops — it does not pause automatically before hard-to-reverse or shared-system actions.
- For review harnesses, decouple *finding* from *filtering* explicitly (report every issue with confidence/severity tags) — Opus 4.8 will literally honor conservative filtering instructions and may under-report otherwise if asked to self-filter in one pass.
- Add an explicit anti-overengineering instruction to prevent unrequested abstractions, files, or defensive code beyond what was asked.
- Front-load a complete task spec in the first turn of interactive sessions — it reasons more, and spends more tokens, after each subsequent user turn.

## Ready-to-use review-prompt skeleton

This is the shape `$alaa-workflow`'s own phase-prompt-pack template already uses for Opus review — reuse it rather than inventing a new one:

```text
<role>Staff-level reviewer. Be skeptical, concrete, and evidence-based.</role>
<context>Read first: <files/plan/diff>. </context>
<must_check>Correctness, production readiness, security, observability, performance, clean code, architecture,
tests that would fail against plausible broken implementations, and validation evidence.</must_check>
<output_format>1. VERDICT (APPROVED | APPROVED-WITH-NITS | CHANGES-REQUESTED) 2. BLOCKERS (file:line, why, fix)
3. RISKS/NITS 4. OUT-OF-SCOPE RECOMMENDATIONS 5. WHAT'S GOOD 6. GATE EVIDENCE</output_format>
```

## Caveats

Figures such as the 64k `max_tokens` starting point, the 1,024-token cache minimum, and cited "up to 30%"/"2.5x" performance deltas are Anthropic-stated, time-sensitive internal figures — re-check the live docs before hard-coding them elsewhere. This model postdates a typical training cutoff; all claims here came from a live fetch, not memory.
