# GPT-6 in Codex

Use this reference for the active GPT family. For a documented legacy exception or a
controlled historical comparison only, read `references/10-gpt-5-6.md`.

## Three separate contracts

1. **Official capability:** model pages describe model and API behavior. They do not prove
   that an account, Codex host, or custom agent exposes that capability.
2. **Runtime capability:** the current Codex tool schema and effective configuration decide
   available models, efforts, tools, permissions, and override behavior. Read
   `references/11-codex-runtime-features.md` before relying on them.
3. **Local policy:** `assets/codex-model-policy.json` owns role-to-model/effort pins and their
   rationale. Its dated supported-effort snapshot is a validation boundary, not a guarantee
   of future availability. Revalidate against the target host before dispatch.

## Starting points and local routing

The official Codex subagent guide recommends starting Sol at `medium`, Luna at `high`, and
Astra at `low`; it recommends more effort for complex or security-sensitive review. Those
starting points are not measured results for this pack.

This pack uses Sol for most engineering, Luna for bounded evidence and procedure execution,
and Astra for difficult design and independent judgment. Exact role pins, including
deliberate departures from the generic starting points, live only in the policy JSON.
All migrated pins start with `calibration_status: unrun`; only recorded comparative evidence
can change that status. Model and effort are separate choices; use
`references/50-effort-and-thinking.md` for calibration and exceptions.

## Prompt design

- Give the outcome, scope, authority, required evidence, output shape, and stop conditions.
  Keep fixed ordering only where order affects correctness.
- Use a small router and precise triggers; load references when their condition applies.
  Preserve the required facts and exception paths when removing duplicated instructions.
- Keep task-relevant tools and examples that resolve a real ambiguity. Compare task quality,
  evidence, and scope compliance before crediting lower token use or fewer calls.
- Advisory requests authorize inspection and reporting. Requested implementation authorizes
  scoped local edits and non-destructive validation. Installation, commit, merge, publication,
  deployment, destructive actions, and external writes require the applicable explicit authority.
- Preserve focused implementer checks and independent acceptance gates. Remove repeated
  checking only when no change, failure, or unresolved concern justifies it.
- Give explicit delegation scope when delegation is authorized; the runtime's current tools
  and higher-priority instructions determine whether and how it can execute.

## API is not the Codex harness

API reasoning parameters, asynchronous tool calling, cache controls, Pro modes, or API
multi-agent features do not become Codex configuration keys by appearing in a model guide.
Verify each on the surface being configured. Do not transfer API `none` effort to Codex
when its active host exposes only reasoning efforts. Do not infer tool access from a model ID.
