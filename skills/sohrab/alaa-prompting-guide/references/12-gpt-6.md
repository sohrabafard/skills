# GPT-6 in Codex

Use this file for the active GPT family: GPT-6.2 Astra, GPT-6.2 Sol, GPT-6.1 Terra and GPT-6 Luna. For an explicit user request for a legacy model, read `references/90-model-selection.md`, and refresh each legacy fact from its official source.

## Three separate contracts

1. **Official capability.** The model pages describe model and API behavior. They prove no exposure by an account, a Codex host or a custom agent.
2. **Runtime capability.** The current Codex tool schema and effective configuration decide the models, efforts, tools, permissions and overrides. Read `references/11-codex-runtime-features.md` before you rely on one.
3. **Capability registry.** `assets/codex-model-policy.json` owns supported pairs and the model-neutral identity of each role and artifact. Its dated snapshot guarantees no host availability.

To select a task pair, read `references/90-model-selection.md`; it holds the source guidance and names the owner of task allocation.

## Source starting points

The Codex models page (18 November 2026) names GPT-6.2 Astra for "demanding projects, such as diagnosing a bug across services" and GPT-6.2 Sol for "everyday tasks like editing code, drafting a report, or turning project notes into a plan". For both it says to "start with the effort your client selects"; for Luna it says to start at High. It also says: "Reasoning efforts don't map exactly between model generations." Carry no effort from a GPT-6 or GPT-6.1 pair to a GPT-6.2 pair; read the current row.

The model-selection guide (18 November 2026) says to "start with the lightest setting that meets your acceptance criteria" and gives eight pairs:

- Luna low: small file edits and field extraction with a clear expected result. Luna xhigh: updates across apps, follow-up priorities, problems with clear constraints.
- Terra medium: desktop apps, record updates, and "focused fixes you can verify".
- Sol medium: bugs and features in an existing codebase, documents for review. Sol xhigh: multistep tasks that need testing and revision.
- Astra low: a clear brief to polished work. Astra medium: planning and carrying out complex projects. Astra xhigh: open-ended problems with trade-offs and assumptions to test.

`references/90-model-selection.md` holds the selector matrix.

Planning on a strong workhorse at medium or high and selecting a mechanical implementation pair are separate choices (reverified 8 October 2026). A finite enumerated batch is local task policy, not a vendor file-count guarantee. These sources establish neither Luna incapability nor equivalence with a Claude model.

## GPT-6.2 behavior

Sources: [Prompting GPT-6.2 in Codex](https://learn.chatgpt.com/guides/prompting-gpt-6-2-astra) and the [latest-model guide](https://developers.openai.com/api/docs/guides/latest-model), both read 18 November 2026. The first says its techniques apply to GPT-6.2 Astra and GPT-6.2 Sol. Neither states these behaviors for Terra or Luna.

| Documented behavior | What to write |
|---|---|
| Writing is "more concise and direct by default" | Remove a general concision line. Keep a length limit that a consumer needs, with its reason |
| With unclear intent, it "may propose a next step and wait for confirmation" | For a long task, authorize reasonable reversible assumptions and require that the agent states them. Name the stop cases: a significant scope change, a concrete block, a decision that belongs to the user, and an irreversible or destructive action |
| It "can carry shorthand from its reasoning or from other agents into its final answer" | Require a self-contained final answer for a reader who saw no progress update |
| Higher effort helps it "stick with a long-running task through the final checks" | State what counts as finished and where the work must be exhaustive. Effort by depth of investigation: `medium` for a quick survey, `high` to trace one suspected cause across several systems, `xhigh` when several causes can interact |
| Below `ultra` it delegates only on request. "Use subagents as needed" lets Codex decide when and how to split. At `ultra` Codex "decides on its own when to bring in subagents" | `references/06-invocation-and-composition.md` owns the delegation wording |

Two vendor texts name an owner in this pack and change no rule there:

- The sample coding prompt says to "skip new tests unless requested, required by the repo, or needed to catch a specific regression existing tests would miss". `/alaa-testing-strategy` owns owed tests.
- For agents that share a machine, the Codex guide says to limit concurrent builds and tests, to leave CPU and memory for other work, and to stop started background jobs and remove created temporary files at the end. `alaa-testing-strategy references/110-execution-resources.md` owns execution resources.

## Prompt design

- Give the outcome, scope, authority, required evidence, output shape and stop conditions. Fix an order only where order affects correctness.
- The skills blog (16 November 2026) says to avoid writing a skill as a step-by-step itinerary and to remove an instruction for behavior the model now does itself.
- Use a small router and precise triggers, and load a reference when its condition applies. When you remove a duplicated instruction, preserve the required facts and exception paths.
- Keep task-relevant tools, and keep an example that resolves a real ambiguity. Check task quality, evidence and scope compliance before you credit lower token use or fewer calls. Vendor lean-prompt guidance proves no fixed quality or cost gain for every task.
- An advisory request authorizes inspection and reporting. A requested implementation authorizes scoped local edits and non-destructive validation. Installation, commit, merge, publication, deployment, a destructive action and an external write each need the applicable explicit authority.
- For a reversible low-impact edit, require discriminating evidence that fits the change. A generic test reminder creates no new suite, and repository-mandated checks still apply.
- Before you remove verification language, read `references/80-subagent-authoring.md`. For delegation wording, read `references/06-invocation-and-composition.md`.

## API is not the Codex harness

An API reasoning parameter, asynchronous tool calling, a cache control, a Pro mode or an API multi-agent feature is not a Codex configuration key. Verify each on the surface you configure, and infer no tool access from a model ID.

- GPT-6.2 Astra and GPT-6.2 Sol (18 November 2026): each API model page says that the API rejects reasoning effort `none`. The latest-model guide says to start a new integration at `medium` and to replace `none` or `minimal` with `low`. The host model catalog (client 0.169.0) lists `low`, `medium`, `high`, `xhigh`, `max` and `ultra` for both, with default `low`. One `codex exec` call at `low` returned for each ID on CLI 0.166.0.
- GPT-6.2 API changes (latest-model guide, 18 November 2026): the Responses API appends top-level `instructions` after `input`, and it drops reasoning items after a mid-conversation edit of the history. Both are API facts.
- GPT-6.1 Terra (3 November 2026): the API page lists `none`, `low`, `medium` (default), `high`, `xhigh` and `max`. The host model catalog lists `low`, `medium`, `high`, `xhigh`, `max` and `ultra`, with default `low` (18 November 2026).
- GPT-6 Luna (Codex models page, 18 November 2026): "supports reasoning efforts up to Max, but not Ultra".
- Never transfer Codex `ultra` to API configuration. Codex `ultra` stays subject to delegation and tool authority.
- Never transfer an API `none` to a Codex host that exposes only reasoning efforts.
- The [Codex models page](https://learn.chatgpt.com/docs/models) requires CLI 0.159.0 or later for `gpt-6.1-terra` and states no minimum for the GPT-6.2 models (18 November 2026). The registry's Terra `recommended_start` records the catalog's `low` metadata.
- Verify the exact pair on the target Codex host. The Codex orchestrator owns task selection and dispatch normalization.

**Subagent inheritance** ([Codex subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents), 18 November 2026). A subagent with no model or effort set inherits the parent agent's model and reasoning effort. A model set at spawn without an effort uses that model's default reasoning effort; an agent file that sets only `model` keeps the previously resolved effort. Resolution order: the value given at spawn, then the `[agents]` default, then the parent; a value in the agent file wins over all three. The page's starting point for a GPT-6.2 Astra or Sol parent is the parent's own model and effort, raised for a subtask that needs deeper investigation and lowered for a quick scan. For Luna chosen explicitly it is `high`.
