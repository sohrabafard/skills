# Build secrets, cache mounts and release evidence

Open this file when a build needs a credential, when a build is slower than its budget, or when a
release must carry evidence of what it contains.

Delivering a secret to a *running* container is a different mechanism and is this skill's
`references/35-secret-delivery.md`.

---

## 1. Build secrets: `RUN --mount=type=secret`

A build argument is recoverable from image history, so `ARG COMPOSER_AUTH` publishes the credential
with the image. The supported mechanism is a secret mount, which exists only for the duration of one
`RUN` and is never written to a layer
(https://docs.docker.com/build/building/secrets/, checked 2026-07-29; the feature is stable and not
marked experimental).

### File form — the default

```dockerfile
# syntax=docker/dockerfile:1
FROM base AS vendor
RUN --mount=type=secret,id=composer_auth,target=/tmp/auth.json,uid=1000 \
    COMPOSER_AUTH_FILE=/tmp/auth.json composer install --no-dev --no-interaction
```

```
docker build --secret id=composer_auth,src=$HOME/.composer/auth.json .
```

The default target is `/run/secrets/<id>` when `target` is not given. `uid` and `gid` matter when
the `RUN` executes as a non-root user, which it does in the stages of the worked Dockerfile in this
skill's `references/10-dockerfile-authorship.md`: without them the mount is root-owned and the
process reads nothing.

### Environment form

```dockerfile
RUN --mount=type=secret,id=npm_token,env=NPM_TOKEN \
    npm ci --no-audit --no-fund
```

```
docker build --secret id=npm_token,env=NPM_TOKEN .
docker build --secret id=NPM_TOKEN .            # shorthand: id and host env var have the same name
```

The variable exists inside that one `RUN` and is not recorded in the image config. `target` and
`env` can be combined to expose the same secret both ways.

### Verifying it did not leak

```
docker history --no-trunc IMAGE | grep -iE 'token|password|secret|auth'
docker inspect --format '{{json .Config.Env}}' IMAGE
docker save IMAGE | tar -tv | head -50
```

The first two must show nothing. The third is the check to run once, after introducing a build
secret for the first time: extract the layers and grep them for the credential. A credential found
in a layer means the image is compromised and the credential is rotated; deleting the image from
the registry is not sufficient, because a pull may already have happened.

## 2. Cache mounts

```dockerfile
RUN --mount=type=cache,target=/tmp/composer-cache,uid=1000,gid=1000 \
    COMPOSER_HOME=/tmp/composer-cache composer install --no-dev --prefer-dist

RUN --mount=type=cache,target=/root/.npm npm ci --no-audit --no-fund
```

A cache mount persists between builds on the same builder and is not part of any layer. It makes a
re-install fast; it does **not** stop a layer being invalidated, so it is not a substitute for the
layer ordering in this skill's `references/10-dockerfile-authorship.md` §3. Both are needed:
ordering decides *whether* the install runs, the cache mount decides *how long* it takes when it
does.

`uid`/`gid` again: a cache mount created for root and used by a process running as 1000 is silently
unwritable, and the package manager falls back to a temporary directory, so the build succeeds and
the cache is never populated. The symptom is a cache mount that never speeds anything up.

`sharing=locked` serialises concurrent builds that use the same cache, which is what a shared runner
needs for a package manager that is not concurrency-safe:

```dockerfile
RUN --mount=type=cache,target=/root/.npm,sharing=locked npm ci
```

Whether a runner keeps a builder between jobs, and whether a registry-backed cache
(`--cache-to type=registry`) is configured, is `/alaa-gitlab-ci-cd` (`$alaa-gitlab-ci-cd`)'s
decision. The Dockerfile side is this skill's.

## 3. Attestations: provenance is on, SBOM is opt-in

**Provenance attestations at `mode=min` are added to images by default**
(https://docs.docker.com/build/metadata/attestations/, checked 2026-07-29). This inverts the older
framing in which evidence was something a policy opted into: today evidence is present unless it is
switched off, and the decisions to make are about level and about SBOM.

| Flag | Effect |
|---|---|
| *(nothing)* | provenance `mode=min`: build timestamp, the frontend used, the materials' digests |
| `--provenance=mode=max` | adds the full build steps, the source of each layer and the build arguments |
| `--provenance=false` | no provenance |
| `--sbom=true` | adds a Software Bill of Materials attestation, generated by scanning the image filesystem |
| `BUILDX_NO_DEFAULT_ATTESTATIONS=1` | disables the default provenance for every build in that environment |

Rules for this fleet:

- **Never `--provenance=false` on a release build.** The only legitimate reason to disable it is a
  registry that cannot store the attestation manifest, and that is a registry problem to fix.
- **`--provenance=mode=max` on release builds only.** `mode=max` records build arguments, so a build
  that passes anything sensitive as `ARG` publishes it in the attestation — a second reason to use
  secret mounts (§1).
- **`--sbom=true` on release builds.** It costs a filesystem scan at build time and is what makes
  "which images contain this CVE" answerable from the registry rather than by rebuilding.
- All BuildKit exporters support attestations. The `local` and `tar` exporters write them to JSON
  files beside the output instead of into the image manifest, which is how an air-gapped release
  carries them.

Reading them back:

```
docker buildx imagetools inspect IMAGE --format '{{json .Provenance}}'
docker buildx imagetools inspect IMAGE --format '{{json .SBOM}}'
```

## 4. Release evidence: what a release records

A release manifest is a file in the deploying repository that answers, for one deployment, three
questions: what was deployed, what it was built from, and what it contains.

```yaml
# releases/2026-07-29-comment-1.4.2.yml
service: comment
tag: 1.4.2
image: registry.takhtenegar.ir/alaa/comment-service:1.4.2
digest: sha256:9f2c...                      # docker buildx imagetools inspect --format '{{.Manifest.Digest}}'
revision: 4a1c9e2f...                       # org.opencontainers.image.revision on the image
base: registry.takhtenegar.ir/docker/octane-base:v1.3.1@sha256:1b7e...
environment: production-swarm
deployed_at: 2026-07-29T09:14:00Z
attestations:
  provenance: max
  sbom: true
scan:
  tool: trivy
  report: artifacts/trivy-comment-1.4.2.json
  critical: 0
  high: 2                                   # both in a base-image package with no fixed version
rollback_to: 1.4.1@sha256:77aa...
```

The `digest` field is the one that makes the rest useful: a tag can be repointed, and a digest
cannot. `rollback_to` is a field rather than an assumption, because "the previous tag" is not
recoverable after two deploys.

## 5. Scanning, without deferring the whole rule to a policy

The older fleet sentence deferred everything to a policy: "fail on critical issues only if policy
requires" and "if no severity policy exists, do not fail builds by default". Followed literally that
produces a scanner that can never fail anything — a gate that gates nothing.

The replacement, which holds with or without a severity policy:

- **The scan runs on every release build**, and its report is a required release artifact. A release
  with no scan report is incomplete regardless of what the report would have said.
- **The merge request states which severities were present**, with a count per severity, taken from
  the report rather than summarised by hand.
- **A CRITICAL finding with a fixed version available blocks the release** until the fix is applied
  or an exception is recorded in the release manifest naming who accepted it and why. That is a
  severity policy; if none exists, this is the one to adopt, because "a fix exists and we did not
  take it" is the only case that needs no judgment.
- Anything beyond that — whether HIGH blocks, how long an exception lives — is
  `/alaa-security-review` (`$alaa-security-review`)'s decision, and *whether* the pipeline fails on
  it is `/alaa-frontend-devops` (`$alaa-frontend-devops`)'s for frontend images and
  `/alaa-gitlab-ci-cd` (`$alaa-gitlab-ci-cd`)'s to express on a runner. This skill states what the
  build produces, not what the pipeline does with it.

Use an open-source scanner. Trivy is the fleet's, and it reads an image reference directly:

```
trivy image --format json --output artifacts/trivy-comment-1.4.2.json \
  registry.takhtenegar.ir/alaa/comment-service:1.4.2@sha256:9f2c...
```

Do not introduce paid SaaS tooling unless it is explicitly requested.

## 6. Build command for a release

```
docker buildx build \
  --file Dockerfile \
  --target runtime \
  --tag registry.takhtenegar.ir/alaa/comment-service:1.4.2 \
  --build-arg VCS_REF="${CI_COMMIT_SHA}" \
  --build-arg OCTANE_BASE_IMAGE="registry.takhtenegar.ir/docker/octane-base:v1.3.1" \
  --secret id=composer_auth,src="${COMPOSER_AUTH_FILE}" \
  --provenance=mode=max \
  --sbom=true \
  --push \
  .
```

Then record the digest, which is the only immutable identifier the deploy should use:

```
docker buildx imagetools inspect registry.takhtenegar.ir/alaa/comment-service:1.4.2 \
  --format '{{.Manifest.Digest}}'
```

`--push` rather than `--load` for a release: an image loaded into a local daemon and then pushed
separately can be modified in between, and the digest recorded would not be the digest deployed.

## 7. Checklist for a build change

1. No credential is passed as `ARG`. (§1)
2. Every cache mount that a non-root `RUN` uses carries `uid` and `gid`. (§2)
3. A release build carries `--provenance=mode=max` and `--sbom=true`. (§3)
4. `mode=max` is not combined with a sensitive `ARG`. (§1, §3)
5. The release manifest records tag, digest, revision, base digest and `rollback_to`. (§4)
6. The scan report exists as an artifact and the merge request states the severity counts. (§5)
7. `docker history --no-trunc` shows no credential. (§1)
