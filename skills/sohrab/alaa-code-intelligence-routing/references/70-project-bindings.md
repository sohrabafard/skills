## Serena context and languages

Choose the context by client capabilities and project lifecycle, not by the HTTP or stdio transport or the containing window. The context is selected at server startup, not negotiated per connected client. Dedicated instances normally use their client's context. An instance shared by Claude Code and Codex can use the generic `ide` context when both provide native file and shell operations; this is a shared-client recommendation, not evidence that client-specific prompts are interchangeable.

Share one HTTP instance only among clients that target the same exact project and worktree, because Serena has one active project. For concurrent different worktrees, recommend separate instances or endpoints, or client-owned stdio processes; never switch a shared instance away from another client's target. With `ide` and a startup project, single-project behavior disables project activation. Without a startup project, do not infer that lock from the context name. Shared project identity does not coordinate concurrent edits.

Inspect the installed context's prompt and effective capabilities. Built-in prompts can prioritize Serena discovery over CodeGraph. During authorized setup, use a custom context with a short pointer to this routing skill and the verified behavior of the client and project. Do not assume an appended pointer removes contradictory instructions. Context tool exclusions alone do not select REPL APIs; use the topic map's REPL owner.

The installed schema owns `<repo>/.serena/project.yml`. Generate it only under setup authority, then merge language entries under its generated selection key; never create both the old and the new key or rename from an old guide.

Enable a backend only for a recurring need for exact-symbol work or refactoring. Start with the material language; add no Markdown, configuration or shell backend just for file coverage. An additional backend requires a named missing guarantee, verified health and an accepted observed resource cost. Remove one only under authorized configuration work when its requirement ends. Record the expected semantic owner, so that backend drift differs from a genuine unsupported operation.
