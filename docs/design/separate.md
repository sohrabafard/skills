# تمرکز سیاست اجرای آزمون در testing-strategy

**خلاصه و تصمیم‌های قطعی**

همهٔ سیاست‌های عمومی اجرای آزمون در `alaa-testing-strategy` متمرکز می‌شوند. skill جدید ساخته نمی‌شود. دو orchestrator مسئول تخصیص agent، وابستگی laneها، ترتیب مراحل و استقلال تأیید باقی می‌مانند.

طبق اصلاح شما، ساخت worktree جدید الزامی نیست. چند agent می‌توانند در یک checkout روی فایل‌های جدا کار کنند؛ هر فایل و منبع مشترک فقط یک مالک فعال دارد.

در این مرحله فقط بررسی انجام شد؛ فایل‌ها تغییر نکردند و validatorها اجرا نشدند.

## ۱. مالکیت و انتقال قواعد آزمون

در [skill آزمون](/home/sohrab/project/skills/skills/sohrab/alaa-testing-strategy/SKILL.md):

- رفتار موجودِ scope tiers، اعتبار و استفادهٔ مجدد از نتیجه، طبقه‌بندی پیش از تعمیر و مدیریت flake حفظ می‌شود. فقط ارجاع‌های لازم برای مالکیت جدید اصلاح می‌شوند.
- سه reference با مسئولیت‌های جدا ایجاد می‌شوند: چرخهٔ اجرای آزمون؛ منابع و اندازه‌گیری؛ طبقه‌بندی نتیجه. router موجود مسیر خواندن آن‌ها را تعیین می‌کند.
- سیاست‌های عمومی از هر دو orchestrator منتقل می‌شوند: اجرای سنگین، priority، concurrency، timeout، محدودیت container، انتخاب موارد آزمون، جمع‌آوری شکست‌ها، تعمیر دسته‌ای، وضعیت نتیجه، شواهد اجرا و محدودیت تغییر محیط هنگام verification.
- بخش عمومی قواعد browser و service reuse نیز منتقل می‌شود؛ از جمله حفظ انتخاب صریح Chromium، استفاده از سرویس اعلام‌شده و منع توقف فرایندهای نامرتبط.
- تعریف قواعد از محل قبلی حذف و با ارجاع شرط‌دار کوتاه جایگزین می‌شود. تاریخچه و گزارش‌های آرشیوی تغییر نمی‌کنند.

چرخهٔ مشترک اجرا چنین خواهد بود:

1. فهرست فرمان‌ها، ورودی‌ها، وابستگی‌ها، observer و شواهد قابل‌استناد مشخص شود.
2. همهٔ بررسی‌های مستقل و قابل‌اجرا جمع‌آوری شوند؛ شکست اول، بررسی مستقل بعدی را متوقف نکند.
3. شکست‌ها طبقه‌بندی و در یک نوبت تعمیر شوند. استثنای فعلیِ تعمیر حداقلی برای مانعی که بیشتر بررسی‌ها را متوقف کرده، حفظ شود.
4. پس از تعمیر، کل فهرست ثبت‌شده روی snapshot ثابت دوباره اجرا شود؛ قواعد فعلی اعتبار نتیجه و بودجهٔ توقف حفظ شوند.

انتخاب یا ادامهٔ implementer و الزام observer مستقل در مرز تعیین‌شده، در orchestrator باقی می‌ماند. اجرای مستقیم همین سیاست را بدون وابستگی به وجود agentهای orchestrator مصرف می‌کند.

## ۲. منابع، اندازه‌گیری و بارگذاری مستقل

- در هر میزبان، اجرای CPU-heavy تحت این workflow هم‌پوشانی نداشته باشد. parallelism داخلی همان فرمان مطابق بودجه مجاز است.
- مجموع سقف CPU کانتینرهای هم‌زمانِ آزمون و وابستگی‌های آن‌ها از ظرفیت قابل‌استفادهٔ میزبان فراتر نرود. محدودیت CPU هر container و تعداد workerهای آن صریح و سازگار باشند؛ priority جایگزین این محدودیت نیست.
- مقایسهٔ زمان فقط با میزبان بدون بار رقیب، workload یکسان، سقف CPU یکسان و شرایط یکسان cache و setup معتبر باشد. اجراهای قبل و بعد به‌صورت درهم‌آمیخته انجام شوند.
- گزارش زمان شامل ترتیب و تعداد اجراها، نمونه‌های خام، دقت timer، پراکندگی و انحراف از شرایط تعیین‌شده باشد. اجرای آلوده یا اختلاف کوچک‌تر از قدرت اندازه‌گیری، مبنای ادعای بهبود نباشد. آزمون flake روی میزبان پربار همچنان مجاز است.
- پیاده‌سازی runnerهای Bash و Windows به skill آزمون منتقل شود. مسیرهای فعلی orchestrator با wrapper نازک حفظ شوند؛ آرگومان‌ها، exit code و خروجی تغییر نکنند. نبود مالک مشترک خطای روشن بدهد و نصب خودکار انجام نشود.
- description، شرایط کاربرد و metadata مهارت آزمون، طراحی و اجرای verification را نیز پوشش دهند؛ حتی وقتی تغییر مربوط به workflow یا script است و آزمون محصول جدیدی نوشته نمی‌شود.
- هر دو orchestrator، نقش‌ها و templateهای مرتبط، و مسیرهای تولید workflow، پیش از طراحی مرحلهٔ implementation یا verification این skill را بارگذاری کنند. ارجاع معکوسِ فعلی که اجرای عمومی آزمون را متعلق به orchestrator می‌داند حذف شود.

## ۳. مالکیت فایل و ادامهٔ امن کار

مالک این قواعد، [مرجع workspace در workflow](/home/sohrab/project/skills/skills/sohrab/alaa-workflow/references/workspace-and-integration.md) خواهد بود:

- مالکیت بر مبنای فایل، خروجی تولیدی و وضعیت اجرایی مشترک تعیین شود. جدابودن فایل‌ها، تعارض روی generator، fixture، container یا سرویس مشترک را مجاز نمی‌کند.
- قبل از تحویل محدودهٔ یک نویسندهٔ متوقف‌شده به نویسندهٔ جایگزین، نبود فرایند و فرزندان فعالِ مرتبط، ثبات فایل‌های محدوده و وضعیت journal یا issue/checkpoint موجود بررسی و با هم تطبیق داده شوند.
- وضعیت مبهم، نوشتن در همان محدوده را متوقف کند؛ کار مستقل ادامه یابد. توقف خودکار فرایند دیگران مجاز نشود.
- ادامهٔ کار در همان checkout و با حفظ diff موجود انجام شود. ساخت worktree یا انتقال diff به مسیر جدید، نتیجهٔ خودکارِ توقف نباشد.
- پس از compaction، مالک زنده و معتبر حفظ شود؛ بازیابی context به‌تنهایی انتقال مالکیت محسوب نشود.
- هنگام validation، نوشتن در ورودی‌های همان gate متوقف باشد. ثبت وضعیت و مالکیت از سازوکار موجود استفاده کند؛ journal یا سامانهٔ قفل تازه ساخته نشود.

## ۴. پیاده‌سازی و معیار پذیرش

ترتیب اجرا: انتقال مالک‌ها و runnerها؛ اصلاح مصرف‌کنندگان و workflow؛ اصلاح checkerها و generated artifacts؛ سپس verification و بازبینی مستقل.

Checkerهای فعلی برخی قواعد را در فایل‌های orchestrator جست‌وجو می‌کنند. این بررسی‌ها به مالک جدید متصل شوند و حذف قاعده، ارجاع شکسته، بازگشت تعریف تکراری و اختلاف رفتاری دو runtime را رد کنند. gate برای پذیرش محل جدید ضعیف نشود.

سناریوهای ضروری:

- اجرای مستقیم بدون orchestrator و هر دو مسیر orchestrated به یک سیاست برسند.
- شکست مستقل، وابستگی شکست‌خورده، contamination و استثنای تعمیر زودهنگام درست تفکیک شوند.
- انتخاب خالی آزمون PASS نشود؛ collect-only معتبر با اجرای واقعی اشتباه نشود.
- oversubscription، worker نامتناسب و مقایسهٔ زمانی آلوده رد شوند.
- نویسنده‌های فایل‌های جدا مجاز و نویسنده‌های متعارض مسدود باشند؛ resume هیچ worktree تازه‌ای نسازد.
- wrapperهای قبلی، آرگومان و نتیجهٔ runner مشترک را حفظ کنند.

فرمان‌های الزامی از ریشهٔ repository:

```bash
python scripts/validate_sohrab_skill_pack.py
python scripts/check_skill_index.py
python scripts/check_fleet_references.py
python scripts/check_lifecycle_contract.py
python skills/sohrab/alaa-codex-orchestrator/scripts/validate_pack.py
python skills/sohrab/alaa-cc-orchestrator/scripts/validate_pack.py
```

علاوه بر این‌ها، contract checkerهای تغییرکرده و self-test آن‌ها، بررسی generated artifacts و grantها، و validation متناسب runnerها اجرا شوند. اجرای پوشش‌داده‌شده در aggregate بی‌دلیل تکرار نشود. نبود محیط Windows یا هر ابزار لازم، صریحاً به‌عنوان شکاف گزارش شود.

پذیرش نهایی نیازمند مالک واحد برای هر قاعده، تطابق رفتاری دو orchestrator، خروج موفق gateهای الزامی و بازبینی مستقل قراردادهاست. اعتبارسنجی ساختاری، اثبات رفتار live agent محسوب نمی‌شود. commit، نصب و انتشار در این دامنه نیست.

## ۵. پیشنهادهای بعدی برای کوچک‌ترکردن orchestrator

این موارد برای تصمیم بعدی گزارش می‌شوند و در انتقال فعلیِ سیاست آزمون اجرا نمی‌شوند. محل اصلی بررسی، [مرجع مراحل و gateها](/home/sohrab/project/skills/skills/sohrab/alaa-codex-orchestrator/references/verification-and-gates.md) و بدنهٔ دو orchestrator است.

| مسئولیت فعلی | مالک پیشنهادی | تغییر پیشنهادی و دلیل |
|---|---|---|
| قواعد طول پاسخ، اصلاح گفتار و خروجی کم‌حجم | `alaa-low-noise` و `alaa-prompting-guide` | تعریف قواعد گفتار از orchestrator خارج شود؛ الزام بارگذاری و شکل خروجی هر lane باقی بماند. این قواعد در کار مستقیم هم کاربرد دارند. |
| جزئیات Documentation gate | `alaa-repo-docs` | فهرست بررسی محتوا، لینک، مثال و اندازهٔ سند یک مالک داشته باشد؛ orchestrator زمان اجرای gate و دریافت verdict را تعیین کند. |
| روش انتخاب راه‌حل، مقایسهٔ گزینه‌ها و تصمیم‌های داده | `alaa-system-design` و مالکان تخصصی | روش طراحی به مالک فنی ارجاع داده شود؛ orchestrator کامل‌بودن تصمیم‌ها را پیش از dispatch کنترل کند. ارجاع‌های موجود نقطهٔ شروع این جداسازی‌اند. |
| روش جست‌وجوی قابلیت و زیرساخت قابل‌استفادهٔ مجدد | `alaa-memory-os` و `alaa-services-contract` | مراحل inquiry از Stage A خارج شود؛ orchestrator نتیجه، مالک و blocker را در برنامه مصرف کند. |
| جزئیات commit و integration handshake | `alaa-workflow` | قواعد عملیاتی تکرارشده به owner فعلی ارجاع داده شوند؛ زمان رسیدن به مرز integration و کنترل اختیار در orchestrator بماند. |

تخصیص نقش و model/effort، استقلال reviewer و verifier، ترتیب وابستگی‌ها، تطبیق خروجی laneها، حل تعارض و شرایط توقفِ هماهنگی، مسئولیت‌های اصلی orchestrator باقی می‌مانند.
